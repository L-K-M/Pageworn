# M3 report: the durable download path

Date: 21 November 2026. Target: the [M3 exit check](../06-delivery-and-tests.md#milestones), against the local Audiobookshelf v2.38.0 reference instance with a disposable non-admin account, through two fault-injecting proxies.

## 1. Delivered

- **Download.** A Download tap on a Library row or in details reads a fresh manifest through a usable route and checks the download permission, the format matrix and the space before it creates a job. A second tap attaches to the same job. A refusal for the book itself (download disabled, unsupported format, no audio) shows on its row; a refusal for the server or its routes repeats Library's status line with its action, as a refresh would.
- **The queue.** One book transfers at a time, in a user-initiated data transfer job that asks for a network of any type and posts a progress notification. Each job lives in Room: queued, transferring, waiting for connection, paused, recoverable failure with its category, verifying, complete or cancelled.
- **Safe continuation.** Every file continues only from the bytes on disk, on the same URL, with a strong validator: a strong entity tag, or the `Last-Modified` date when the response's `Date` is at least 60 s later. Audiobookshelf sends only weak tags, so the date is what Pageworn sends in `If-Range`. A full response's validator is stored before its first body byte, so a pause or a process death mid-file leaves a prefix that continues. A malformed range keeps the prefix; a second one stops the job. A full 200 replaces the partial from zero. A changed route restarts a partial file from zero and reuses complete files that the fresh manifest still identifies.
- **Faults.** A dropped connection and a 5xx retry with backoff (5 s doubling to 10 minutes). A 403 stops at once with the download-disabled category; a persistent 404 stops after one refetch of the item; a 204 with `X-Accel-Redirect` stops with the no-audio category. None of these retries by itself, and Retry reads a fresh manifest first.
- **Addresses.** Removing, disabling or signing out of the serving address moves the job to Waiting for connection with its files intact, and it continues through the next usable address. With no usable address it waits and never fails.
- **Space.** Before every file the volume must hold the book's remaining bytes plus 1 GB; otherwise the job rests with "More space is needed to finish this download." and the shortfall, without requesting audio. A write that the phone refuses (a full disk) rests the job the same way and keeps its bytes.
- **Publication.** Every staged track is opened by the player's parser before one Room transaction publishes the edition with its cover. Recovery after a process start republishes a renamed but uncommitted generation, reclaims cancelled ones and queues interrupted work. Cancel commits before it stops anything, so it survives a restart, and a Cancel that loses to publication leaves the book Ready.
- **Screens.** Library, details, Downloaded and the player drive Download, Pause, Resume, Retry, Cancel and Repair. Library rows and details of remote books show the server's cover thumbnail, cached on disk.

## 2. Files and design decisions

- `transfer/`: `TransferCoordinator` (the queue, reconciliation, copy, verification, publication and recovery), `FileTransfer` (one file under the safe-continuation rules), `TransferPorts` (the routes, channels, verifier and scheduler it depends on), `ProbeTrackVerifier`, `TransferJobService` (the job, its scheduler and notification), `SpacePolicy`, `ManifestCheck`, `Validators`.
- `account/AccountTransferRoutes.kt` gives the coordinator manifests and download channels through `ServerAccess`; `server/AbsClient.kt` adds the item, download and cover requests; `catalog/RemoteCovers.kt` caches thumbnails.
- `ui/state/TransferActions.kt` holds the screens' transfer intents; they run in the application scope, so leaving a screen never cancels a pause or a cancel.
- **State ownership.** Room is the only record of a job. Every write is a transactional read-modify-write that checks the job is still the one this run owns, so a Pause, a Cancel or an address change that commits first wins, and a stale run's write is dropped. Progress for display is journaled every 500 ms and never decides a resume; the bytes on disk do.
- **The validator is stored before the body.** A full response's validator and URL fingerprint are saved after the file is emptied and before its first byte is written. Without that, a paused file resumed from zero, which the coordinator's JVM pause test found.
- **A full disk is not a dropped connection.** A refused write is classified as a storage failure that keeps the written prefix, so it rests with the storage-full copy instead of retrying as a network fault.
- **The job replaces its pending self.** The platform still listed a job that had just called `jobFinished`, and keeping it stranded a Resume made right after. The coordinator schedules only while no queue runs in its process and the queue checks once more for work before it ends.
- **Plan changes in this milestone.**
  - [Server contract](../04-server-and-downloads.md): the backoff (5 s doubling to 10 minutes) and the per-file request limit in one attempt; the second malformed response; the refused write; a manifest without file sizes; storing the validator before the body.
  - [Android and data plan](../03-android-and-data.md#android-integration): one job runs the queue, the job is replaced rather than kept, and what the platform did after the process was killed during a job.

Measured on both emulators: the full-disk case rested with a shortfall of 1.00 GB, the 1 GB margin less the 1 MB left free plus the remaining bytes; on the metered network the transfer started 211 ms (API 37) and 359 ms (API 34) after the tap.

The first form of phase 6 allocated the whole filler in one call once the copy had started. On API 34 the copy then failed with the storage-full rest as expected; on API 37 the copy completed instead. The second form allocates all but the margin before the download and the last 1.05 GB during the copy; it passed on API 37, and in the final full run on API 34 the copy completed. The API 34 log showed why: with the volume nearly full, `DeviceStorageMonitorService` had installd purge cached data (about 600 kB, including Pageworn's own cover cache), and the copy wrote its last 2.2 MB into the space that left. The phase now also keeps the volume full while it waits, adding back every purge of more than 64 kB within 50 ms, and passes on both emulators. The app needed no change: a refused write rests the job as storage-full whenever the platform refuses one. Whether the purge also explains the first form on API 37 was not confirmed; that run's log was gone.
